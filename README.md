# DSH-Portable Updates

Machine-readable update assets for [DSH-Portable](https://github.com/WSL043/DSH-Portable).

This repository is an infrastructure channel. Download the application from the [DSH-Portable Releases page](https://github.com/WSL043/DSH-Portable/releases/latest).

The legacy stable and candidate channels mirror one qualified core catalog, with channel-specific download URLs. Its supported window contains up to five of the newest official versions, preserving at least two non-alpha versions when available. Only compatible, qualified versions inside that window are offered; waiting or blocked versions can leave fewer than five choices. Current clients use that catalog for compatible version selection; older clients continue to use the latest-version manifest.

After a run attempts a version, the workflow can dispatch up to two additional queue-drain runs automatically, for at most three runs in the default bounded queue. This fills a new shell's version history without waiting an hour per version. The queue stops when there is no eligible work or its budget is exhausted; scheduled discovery resumes later. Failed versions retain their cooldown and do not block other candidates. Explicit rebuild and accepted-only runs do not drain the queue.

The build-time permission verifier uses the published patcher's read-only no-change check, including both ends of the newer upstream permission slot. A narrowly checked adapter updates the stale 0.6.9 verifier without changing the published desktop. Unknown verifier shapes fail for review; core artifact acceptance and compatibility fingerprints remain required.

When a new Portable baseline advances its bundled core, automatic discovery can also qualify older cores inside the supported window. Cores already offered for the same shell contract retain their qualification; other cores still need compatibility checks and acceptance. Deprecated versions remain excluded. Backfilling history preserves the newest accepted core as the default update, so adding rollback choices never pushes a downgrade. The shared qualification workflow processes one version per run, prioritizing newer eligible versions.

GitHub Actions scans all official npm registry versions every hour (at minute 17; GitHub may delay scheduled jobs), rather than relying on moving dist-tags. The shared window can include final, Alpha, Beta and RC releases; stable and candidate do not apply separate release-type policies. Discovery skips deprecated or incomplete registry entries and selects one unverified in-window version at a time from newest to oldest. A new release must have registry integrity and an official Git tag resolving to an immutable source commit before its source metadata is resolved. Versions awaiting their source tag are skipped until a later run. Qualification records live in `update-channel-core/qualification-state.json`, merging legacy channel records; failed attempts cool down for 24 hours, and a new Portable source SHA is retried independently.

The workflow uses the published stable Portable release tag and the matching successful Portable main build as its shell baseline, then carries one discovered source lock through all build and acceptance jobs. Windows x64, macOS x64/arm64 and Linux x64/arm64 must all pass installation, startup, command, default-plugin preservation and rollback checks before that channel publishes. Failed builds leave the current catalog intact and remain visible in Actions; the next candidate can be selected during the failed version's cooldown. Successful versions appear automatically in the compatible client's version selector; no source-lock PR or manual merge is required for core updates. A new shell or interface requirement still requires a Portable product update.

`official-core.lock.json` beside the published manifests records the exact official version, source commit and build metadata. Versioned lock and source metadata assets retain each qualified version for catalog history. This pipeline publishes core components only. It does not publish full Portable releases or automatically port source changes into the Portable repository.

The exact upstream checkout supplies its publishable package membership through the official release planner, including private-package exclusions. This packaging adapter is maintained here independently of Portable releases. A pipeline correction retries previously failed versions immediately while retaining successful qualification records; ordinary failures on an unchanged pipeline keep the 24-hour cooldown. See [the architecture notes](ARCHITECTURE.md) for compatibility and maintenance boundaries.

If a newer upstream release requires additional adaptation, manually dispatch with `accepted_only=true` to select the already accepted in-window core against the latest verified shell. Registry integrity and same-contract retention rules still apply; any required build runs the complete platform build and acceptance matrix before publication. Scheduled runs continue discovering and backfilling the supported five-version window while the existing interfaces remain compatible. An interface break still requires a Portable product change, and this option does not mark a failed new version as accepted.

## Published Native shell boundary

The current workflow selects the latest **published stable Native** Portable release and its matching successful main build as one shell baseline. Both legacy channel catalogs receive that qualification result. It does not run a separate Portable RC qualification lane, and an unpublished main commit is never selected as a shell baseline.

The baseline selector identifies Native releases by their published manifest, Windows offline ZIP and checksums assets. Electron releases in the same repository are a separate product line and never become a Native core baseline merely because they were published more recently. The exact release tag and successful build checks still apply after selection.

This does not loosen compatibility checks or claim a tested core works on every shell. Same-contract retention preserves the existing qualification boundary; an interface change still requires the appropriate shell and core qualification.

Windows core qualification also operates the bundled plugins inside the updated product's hidden native WebView2, in both themes. A synthetic keyless session exercises image annotation and draft return, session deletion confirmation/cancellation and continued input. It records screenshots and catches React/overlay errors that do not emit browser `pageerror`. Merely finding an installed plugin in the package list is not UI acceptance. A failure blocks core publication; the workflow does not change user-installed third-party plugins or bypass compatibility declarations.

The UI probe was checked against the actual official 0.1.7-alpha.1 host: the repaired source plugins pass, while the published image-viewer 0.1.2-beta.1 is rejected with the reproduced overlay/icon failure. This positive/negative browser check validates the probe, not the native product or a new plugin release. Native workflow results and screenshots must still be reviewed before claiming product acceptance.
